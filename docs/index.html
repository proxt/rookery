Rookery · документация

Панель, ноды и клиент — от установки до API

Rookery — WebRTC-туннель с центральной панелью, произвольным числом relay-нод и клиентом под Windows. Здесь — как поднять каждую часть, что означает каждая настройка, и справочник по API панели с примерами запросов.

01 Архитектура#

Три независимых компонента. Нода не хранит пользователей и никогда не спрашивает у панели «а этот токен настоящий?» — проверяет сама.

Ключевое архитектурное решение: токен сессии подписан ключом самой ноды, а не общим секретом панели. Нода проверяет подпись локально (HMAC-SHA256), без обращения к панели — значит, установление сессии не зависит от доступности панели в момент подключения.

02 Термины#

Панель
Центральный сервис: хранит пользователей, подписки, список нод и статистику. Один процесс rookeryp, своя SQLite.
Нода
Relay-сервер, который реально гоняет трафик. Не хранит пользователей — только свой node_id/api_key, выданные панелью. Процесс rookeryd, отдельный репозиторий.
Пользователь / подписка
В Rookery это одно и то же: у пользователя один токен, одна ссылка, один набор доступных нод — без отдельной сущности «подписка» поверх пользователя.
Токен сессии
Короткоживущий (по умолчанию 6ч) токен, который панель подписывает ключом конкретной ноды при каждом запросе /sub/{token}.

03 Быстрый старт#

От пустого VDS до первого подключения клиента.

  1. Поднять панель
    bash
    mkdir -p ~/rookery-panel && cd ~/rookery-panel
curl -O https://raw.githubusercontent.com/proxt/rookery/master/panel/deploy/docker-compose.yml
sudo docker compose up -d
sudo docker compose logs   # тут будет пароль администратора
  2. Зайти в /admin, добавить ноду

    Вкладка «Ноды» → «Добавить ноду» → скопировать выданные node_id и api_key.

  3. Поднять ноду с этими данными
    bash
    mkdir -p ~/rookery-node && cd ~/rookery-node
curl -O https://raw.githubusercontent.com/proxt/rookery-node/master/deploy/docker-compose.yml
cat > node.yaml <<EOF
panel_addr: "http://127.0.0.1:8090"
node_id: "<выдано панелью>"
api_key: "<выдано панелью>"
EOF
sudo docker compose up -d
    Локальный адрес панели

    Если нода и панель на одном хосте, panel_addr — http://127.0.0.1:<порт>: нода стучится по внутреннему адресу, а публичный домен ей не нужен.

  4. Создать пользователя и привязать ноду

    Вкладка «Пользователи» → «Добавить» → открыть карточку → вкладка «Ноды» → отметить нужные → «Сохранить». Ссылка — во вкладке «Инфо».

  5. Вставить ссылку в клиенте

    Вкладка «Подписки» → вставить rookery://sub/… (или обычную https-ссылку — работают обе) → «Добавить» → выбрать сервер → «Подключить».

04 Панель · установка#

Панель — чистый HTTP-сервис (без WebRTC/ICE), поэтому обычный docker compose без host-сети.

panel/deploy/docker-compose.yml
services:
  rookery-panel:
    image: ghcr.io/proxt/rookery-panel:latest
    container_name: rookery-panel
    restart: always
    ports:
      - "127.0.0.1:8090:8090"
    volumes:
      - rookery_panel_data:/data

volumes:
  rookery_panel_data:

Ничего настраивать вручную не нужно: при первом запуске панель сама генерирует логин администратора и печатает пароль один раз в docker compose logs — сохраните его, второй раз не покажется.

Порт слушает 0.0.0.0, не 127.0.0.1

Панель специально слушает все интерфейсы внутри контейнера — иначе трафик, пришедший через проброс порта Docker (bridge-сеть), не долетает до процесса. Наружу доступ уже ограничен строкой 127.0.0.1:8090:8090 в compose-файле, поэтому снаружи порт всё равно закрыт без Caddy.

05 Автообновление#

Compose-файл уже содержит watchtower — он раз в 5 минут проверяет ghcr.io и сам перезапускает контейнер на новом образе. Ручной docker compose pull && up -d после пуша в master не нужен ни панели, ни ноде.

ПараметрЗначение
--interval300 секунд
--cleanupудаляет старый образ после обновления
Простой при обновлениинесколько секунд на перезапуск контейнера

Как проверить, что обновление реально применилось

Внизу боковой панели администратора — под именем текущего админа — есть строка «Обновлено: …». Это не время последнего опроса watchtower, а момент сборки именно того образа, который сейчас выполняется (панель встраивает время сборки и commit в бинарь через -ldflags при CI-сборке и отдаёт их на GET /admin/api/version). Если после пуша в master эта дата не сдвинулась через 5–10 минут — watchtower не смог обновить контейнер.

Панель и нода на одном хосте

У watchtower есть штатное поведение: увидев на хосте больше одного своего контейнера, он считает второй «устаревшей копией себя» и останавливает его — если панель и нода развёрнуты на одном сервере, их отдельные watchtower-сайдкары будут убивать друг друга. Оба compose-файла ставят WATCHTOWER_SCOPE (свой на панель, свой на ноду) — это единственное, что их разводит; убирать эту переменную при совместном хостинге нельзя.

06 Управление нодами#

Вкладка «Ноды». Каждая нода — имя, публичный адрес и теги (страна/метка) для группировки.

При создании панель выдаёт api_key — это единственный раз, когда его показывают полностью в форме создания (позже он всё ещё виден в карточке ноды, но храните его так же бережно, как пароль: им подписываются токены сессий для этой ноды).

Карточка ноды показывает статус online / offline (по heartbeat, окно 2 минуты), время последнего heartbeat и суммарный трафик через эту ноду.

07 Пользователи и подписки#

Пользователь = подписка: у каждого один токен, одна ссылка, свой набор нод. Карточка пользователя открывается по клику на строку и разбита на три вкладки.

Инфоимя, переключатель «активна», начало/окончание действия, ссылка подписки с копированием
Нодычекбоксы — какие ноды доступны этому пользователю
Статистикатрафик всего + график за последние 7 дней

08 Статистика#

Вкладка «Обзор»: число пользователей, нод онлайн, трафик за 24ч и всего, график трафика с переключением диапазона (24ч / 7д / 30д). Те же данные доступны для отдельного пользователя или ноды через их карточки — см. также API статистики.

09 Администраторы#

Логинов в панель может быть сколько угодно — не общий на всех, а свой у каждого.

  • Создать нового — вкладка «Админы», логин + пароль от 8 символов.
  • Удалить нельзя себя и нельзя последнего оставшегося админа — панель откажет с 400.
  • Смена собственного пароля — там же, требует текущий пароль.

10 Обновления клиента#

Панель одновременно раздаёт билды клиента: вкладка «Обновления» — загрузить установщик (версия + заметки + файл), список загруженных версий, у каждой — кнопка «Скачать» (публичная ссылка, работает и без приложения) и удаление.

Последняя загруженная версия автоматически становится «актуальной» — её видит клиентское приложение при проверке обновлений (кнопка «Проверить обновления» в Настройках клиента, сверяет со своей версией).

11 API панели · аутентификация#

Все /admin/api/* эндпоинты, кроме логина, требуют cookie-сессию. Ниже — примеры на curl со сквозным cookie-файлом.

POST /admin/api/login

Тело: {"username": "...", "password": "..."}. При успехе ставит cookie rookery_admin_session (24ч) и отвечает 204.

bash
curl -c cookies.txt -X POST https://panel.example.com/admin/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"..."}'
POST/admin/api/logoutтребует сессию

Отзывает текущий токен сессии.

GET/admin/api/sessionтребует сессию

Возвращает текущего админа: {"id": "...", "username": "..."}. Способ проверить, что сессия ещё жива.

12 API панели · пользователи#

GET/admin/api/usersтребует сессию

Список всех пользователей с их нодами и ссылкой подписки.

POST/admin/api/usersтребует сессию

Тело: {"name": "..."}. Создаёт пользователя со случайным токеном.

bash
curl -b cookies.txt -X POST https://panel.example.com/admin/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Иван"}'
GET/admin/api/users/{id}требует сессию

Один пользователь по ID.

PUT/admin/api/users/{id}требует сессию

Тело: {"name", "enabled", "starts_at", "expires_at"}. Даты — RFC3339 или пустая строка (без ограничения).

PUT/admin/api/users/{id}/nodesтребует сессию

Тело: {"node_ids": ["..."]}. Полностью заменяет набор нод пользователя.

DELETE/admin/api/users/{id}требует сессию

Удаляет пользователя и его статистику. Старая ссылка сразу перестаёт работать.

13 API панели · ноды#

GET/admin/api/nodesтребует сессию

Список нод с api_key, статусом и временем последнего heartbeat.

POST/admin/api/nodesтребует сессию

Тело: {"name", "address", "tags"}. Возвращает ноду вместе со свежесгенерированным api_key — его вписывают в node.yaml той ноды.

PATCH/admin/api/nodes/{id}требует сессию

Тело: {"name", "address", "tags", "enabled"}.

DELETE/admin/api/nodes/{id}требует сессию

Удаляет ноду. Развёрнутый процесс ноды продолжит отвечать, но токены для неё панель больше не подпишет.

15 API панели · релизы#

GET/admin/api/releasesтребует сессию

Список загруженных версий, новые сверху.

POST/admin/api/releasesтребует сессию

multipart/form-data: поля version, notes, файл в поле file. Лимит — 500 МБ.

bash
curl -b cookies.txt -X POST https://panel.example.com/admin/api/releases \
  -F "version=0.3.0" \
  -F "notes=Список изменений" \
  -F "file=@rookery-amd64-installer.exe"
DELETE/admin/api/releases/{id}требует сессию

Удаляет версию из списка и файл с диска.

16 Публичные эндпоинты#

Без cookie-сессии — их дёргает клиент и произвольные посетители по прямой ссылке.

GET/sub/{token}

Открытая в браузере — красивая HTML-страница подписки с кнопкой «Установить в приложение». С заголовком Accept: application/json (так делает клиент) — чистый JSON со списком нод и подписанным токеном сессии для каждой.

rookery.example.com/sub/8f2a1c…

Установить в приложение Скопировать ссылку

Так видит ссылку любой браузер — открытая с Accept: text/html. Кнопка «Установить» — это тот же rookery://-диплинк, что и в клиенте.

GET/releases/latest

Метаданные последнего загруженного релиза — то, что опрашивает апдейтер клиента.

GET/releases/{id}/download

Сам файл, с Content-Disposition: attachment.

17 Нода · установка#

Нода живёт в отдельном репозитории — proxt/rookery-node — и не требует ничего из репозитория панели для сборки. Сначала зарегистрируйте ноду в панели (см. Управление нодами), затем:

bash
mkdir -p ~/rookery-node && cd ~/rookery-node
curl -O https://raw.githubusercontent.com/proxt/rookery-node/master/deploy/docker-compose.yml
cat > node.yaml <<EOF
panel_addr: "https://panel.example.com"
node_id: "..."
api_key: "..."
EOF
sudo docker compose up -d
network_mode: host не опционален

ICE-агент pion собирает host-кандидаты из сетевых интерфейсов контейнера. В обычной bridge-сети это внутренний адрес Docker (172.x), который снаружи недостижим — с ним подключение клиентов не установится. network_mode: host в compose-файле уже настроен именно поэтому.

18 Нода · без Docker#

Собрать бинарь и запустить как systemd-юнит.

bash
git clone https://github.com/proxt/rookery-node.git
cd rookery-node
make build   # bin/rookeryd — статический линукс-бинарь, CGO_ENABLED=0

sudo mkdir -p /opt/rookery
sudo cp bin/rookeryd /opt/rookery/rookeryd
sudo cp deploy/systemd/rookery-node.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rookery-node

Юнит уже настроен с NoNewPrivileges, ProtectSystem=strict, без лишних capabilities. Пароль/данные ноды не хранятся локально — читать логи не нужно, вся конфигурация в node.yaml.

21 Caddy и домен#

И панель, и нода — обычный HTTP за Caddy, который сам получает TLS-сертификат.

Для ноды

Caddyfile
node.example.com {
	reverse_proxy 127.0.0.1:8080
}

Для панели

Если панель на своём поддомене — так же просто, один reverse_proxy. Если панель и нода делят один домен, маршрутизируйте по пути — панель занимает только эти четыре префикса:

Caddyfile
example.com {
	handle /admin* {
		reverse_proxy 127.0.0.1:8090
	}
	handle /sub/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle /sub-assets/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle /api/nodes/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle /releases/* {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		reverse_proxy 127.0.0.1:8080
	}
}
После правки конфига

caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy — если конфиг невалиден, Caddy откажется применять его и останется на прежнем, так что сайт не упадёт от опечатки.

22 Клиент · GUI#

Windows-приложение на Wails: вкладки Главная / Подписки / Настройки / О программе.

  • Добавление подписки — вкладка «Подписки», вставить ссылку (принимает и rookery://sub/…, и обычную https://panel/sub/{token}). Также срабатывает автоматически по клику на «Установить в приложение» на странице подписки — приложение зарегистрировано обработчиком схемы rookery://.
  • Выбор сервера — разворачиваете подписку, отмечаете нужную ноду.
  • Системный VPN — в Настройках, заворачивает весь трафик ОС через виртуальный адаптер (Wintun), а не только приложения с SOCKS5. Требует прав администратора.
  • Обновления — кнопка «Проверить обновления» в Настройках, см. ниже.

23 Клиент · CLI#

Headless-вариант для серверов/скриптов — тот же движок, без окна.

client.yaml
panel_addr: "https://panel.example.com"
token: "<токен подписки>"
token_env: ""            # или имя переменной окружения вместо token

24 Формат ссылки#

Ссылка кодирует адрес панели и токен подписки, ничего больше — список нод клиент получает, уже обратившись по этой ссылке к панели.

schema
rookery://sub/<base64url(JSON)>

// где JSON:
{ "p": "https://panel.example.com", "t": "<токен>" }

Клиент одинаково принимает и эту схему, и обычную https://panel.example.com/sub/{token} — именно её показывает адресная строка браузера на странице подписки и кнопка «Копировать ссылку».

25 Автообновление приложения#

В отличие от сервера, обновление клиента — по кнопке, не молча в фоне: заменить исполняемый файл на лету, пока он запущен, нельзя.

  1. Проверить

    Настройки → «Проверить обновления» — сверяет версию с панелью активной подписки (GET /releases/latest).

  2. Скачать и установить

    Приложение качает установщик во временную папку, запускает его (наследует уже полученные права администратора — второго запроса UAC не будет) и закрывается само, чтобы установщик мог перезаписать файлы.

26 Протокол · токен сессии#

Токен — не JWT и не что-то стандартное, но устроен похоже: подпись поверх полезной нагрузки.

go
type Claims struct {
    UserID string `+"`json:\"uid\"`"+`
    NodeID string `+"`json:\"nid\"`"+`
    Expiry int64  `+"`json:\"exp\"`"+` // unix seconds
}

// token = base64url(JSON(claims)) + "." + hex(HMAC-SHA256(payload, node_api_key))

Панель подписывает токен ключом той конкретной ноды, для которой он выдан — ключ другой ноды такой токен не провалидирует. Нода проверяет подпись сама, локально, без обращения к панели: время жизни токена (по умолчанию 6 часов) — это и есть механизм отзыва доступа, а не отдельный вызов «можно ли ему».

27 Протокол · транспорт#

Один WebRTC DataChannel на сессию, поверх него — smux мультиплексирует все TCP/UDP-потоки клиента.

СлойНастройка
SCTP (association)окно приёма поднято до 64 МБ — дефолт pion/sctp в 1 МБ иначе ограничивает всю ассоциацию сильнее, чем окно smux
smux (per-stream)4 МБ на поток, 64 МБ на сессию — дефолт 64 КБ ограничивает throughput одного потока до window/RTT
DataChannel (recv)буфер входящих сообщений на 2048 штук — иначе медленный потребитель на одном потоке душит приём для всех остальных

28 Устранение неполадок#

Панель отвечает «connection reset» через Docker

Проверьте listen_addr в конфиге панели — должен быть 0.0.0.0:PORT, а не 127.0.0.1:PORT. При bridge-сети (в отличие от network_mode: host у ноды) трафик от проброса порта приходит на интерфейс контейнера, а не на его loopback.

404 на путях панели через общий домен с нодой

Проверьте, что в Caddy размечены все пять путей панели (/admin, /sub/, /sub-assets/, /api/nodes/, /releases/) — см. пример конфига. Всё, что не попало ни в один handle, уходит на ноду.

Скорость упирается в потолок независимо от канала

Почти всегда — узкое окно на одном из трёх уровней транспорта (SCTP / smux / приёмный канал DataChannel), см. транспорт. Симптом: throughput не растёт с более быстрым сервером — значит, упирается не в канал, а в буфер где-то в стеке.

Нода запускается и сразу падает в перезапуск

panel_addr, node_id и api_key в node.yaml обязательны — без них rookeryd завершается с ошибкой валидации конфига ещё до старта HTTP-сервера. Проверьте docker compose logs.

Watchtower в рестарт-лупе или молчит вместо обновления

Проверьте docker logs <имя>-watchtower. Ошибка client version … is too old значит, что образ containrrr/watchtower:latest старый (последний вышел в конце 2023) и его клиент занижает версию Docker API ниже минимальной, которую понимает движок — задайте DOCKER_API_VERSION в переменных окружения контейнера (см. Автообновление). Если панель и нода на одном хосте, а обновляется только одна из двух — проверьте, что у обоих watchtower задан свой WATCHTOWER_SCOPE, иначе один экземпляр считает другой «своей устаревшей копией» и останавливает его.

Приложение не подхватывает ссылку по клику «Установить»

Схема rookery:// регистрируется инсталлятором в реестре Windows (HKEY_CLASSES_ROOT\rookery) — если приложение стояло до пересборки инсталлятора с этой функцией, переустановите через новый rookery-amd64-installer.exe.
